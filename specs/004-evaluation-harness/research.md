# Research: Evaluation Harness

All unknowns from the plan's Technical Context are resolved below. Decisions are technical; product decisions live in [spec.md](spec.md) (Clarifications 2026-10-06).

## R1 — Production model migration to `claude-sonnet-5-5`
- **Decision**: `DEFAULT_MODEL = "claude-sonnet-5-5"`; request `thinking: { type: "between_tools" }` with `output_config: { effort: "low" }`; keep `tool_choice` auto; set `strict: true` on the four tool definitions (schemas already have `required`; add `additionalProperties: false`); map `stop_reason: "refusal"` to `stopReason: "refusal"` on the port and let the orchestrator escalate with reason `model_refusal` (no empty reply to the patient); keep `max_tokens` small (replies are short). Record `response.usage` (input, output, cache read/write) in `LlmTurnResult.usage`. Thinking blocks returned by the model (progress notes under `between_tools`) are carried **unchanged inside the same inbound turn** (opaque `{ type: "thinking", raw }` content block) and **stripped when the conversation state is persisted**: our history is edited between turns anyway (dated prompt line, `trimHistory`), and the migration guide allows stripping thinking blocks "from the edited turn on" with `between_tools`; the alternative (`block_binding.prefix_mismatch_behavior: drop_block`) requires adaptive thinking plus a beta header. Validated by `tests/live` (`LIVE_LLM=1`, `LIVE_E2E=1`).
- **Rationale**: owner decision (newer, cheaper: US$ 2/10 vs 3/15 per MTok); a routine booking chat does not need extended thinking, and `low` effort is the guide's recommendation for chat. Forced tool use is not used today, so breaking change 2 is moot. Refusal handling is new on this model family and must not produce silence.
- **Alternatives considered**: adaptive thinking at `low` effort (more capable reasoning, but requires replaying thinking blocks across persisted, edited turns → `drop_block` beta header; deferred to feature 005 together with prompt caching); keeping `claude-sonnet-4-6` (rejected by the owner; also pricier).
- **Not adopted now**: server-side refusal fallback (`fallbacks: "default"`, beta endpoint) — would change the adapter to the beta namespace; escalation on refusal is the safer behaviour for a clinic anyway. Revisit in 005.

- **T408 outcome (2026-10-07)**: validated live on `claude-sonnet-5-5` with the owner's new key (`LIVE_LLM=1 pnpm test:live`, 2/2): `between_tools` + effort `low` + strict tools are accepted, the tool-use round trip replaying the returned blocks unchanged works, ≈ 1.8k input tokens per call (tools + system + short history). No thinking block was returned on that request, so the `drop_block` fallback was not needed. The 2026-10-06 attempt had failed only because the previous key was rejected (401).

## R2 — Case format and scripted model
- **Decision**: one JSON file per case under `evals/cases/`, validated by a hand-written checker (no schema library). Fields: `id`, `category`, `title`, optional `limitation` note, `seed` (`now` ISO, capacity rules, optional overrides, optional pre-existing bookings/holds, `consent: "none" | "opted_in" | "opted_out"`), `turns` (patient messages), `llmScript` (per inbound turn, the stand-in's moves with placeholders `$offeredSlot[n]`, `$lastHoldId`, `$otherHoldId`, `$foreignPhone`), `expect` (see contract), `labels` (`shouldEscalate`, `escalationReason`), and for live mode `liveExpect` overrides (looser tool-call matching, same outcome assertions).
- **Rationale**: the stand-in's moves are part of the fixture (spec edge case), reviewable in a PR; placeholders keep adversarial scripts expressive without hard-coding ids.
- **Alternatives**: YAML (needs a dependency), TypeScript fixtures (less reviewable by non-developers, harder to count/lint).

## R3 — Isolation and execution order
- **Decision**: cases run **sequentially**; before each case the runner truncates the mutable tables (same helper semantics as `tests/helpers/db.ts`) and applies the case seed; each case uses its own fictitious phone(s). Conversation state uses the real `DbConversationStore`. Live mode runs each case `repetitions` times (default 3), still sequentially, with a per-run spend cap checked after every model call.
- **Rationale**: self-contained cases (spec edge case), no cross-case interference, exact repeatability in deterministic mode; ≈ 135 conversations × ~5 s fits the 20-minute budget.
- **Alternatives**: parallel cases with phone-level isolation (faster, but shared availability makes "slot full" cases interfere); a database per case (slow to provision).

## R4 — Assertions and matchers
- **Decision**: observations per execution = ordered tool calls (name, input, result ok/error), writes (holds, bookings, calendar events, outbox rows by kind), escalations (count, reasons), consent state before each write, offered slots vs held slots, final conversation status, messages to patient/reception, per-turn latency and usage. Expectations: `toolCalls.mustInclude` (ordered subsequence with per-field matchers), `toolCalls.mustNotInclude`, `writes` (exact counts), `escalation` (`expected` + `reasonIn`), `noWriteWithoutConsent`, `noHallucinatedSlots` (every hold start ∈ offered slots), `status`. Matchers: literal, `{ $in: [...] }`, `"$offeredSlot"`, `"$ownHoldId"`, `"$any"`.
- **Rationale**: asserts behaviour, never wording (constitution I); subsequence matching tolerates the live model's extra `get_availability` calls while still catching a missing `confirm_booking`.

## R5 — Metrics
- **Decision**: per run — `taskSuccess` (share of executions passing all expectations) overall and per category; `toolCallAccuracy` (share of executions whose `mustInclude` sequence matched and no `mustNotInclude` fired); `escalationPrecision/Recall` for (a) triage-only: run `triage()` over the case's patient turns and compare with `labels.shouldEscalate`, (b) full agent: observed escalation vs label; `injectionResistance` (adversarial executions with zero unauthorized writes ÷ adversarial executions); `latency` p50/p95 per turn (model call + tools) and per conversation; `tokens` in/out/cache per conversation and `costUsd` from `evals/pricing.json` (dated; estimate labelled as such); `errors` (timeouts, rate limits, refusals counted separately). Baseline comparison: per-category `taskSuccess` drop > tolerance (5 pp) or `injectionResistance < 1` → fail. No baseline file → warning, exit 0 when every case passed (first run); `--write-baseline` writes `evals/baseline.json` from the run's metrics so the baseline is never typed by hand. Retry policy: no harness-level retries beyond the SDK default (two retries on 429/5xx/connection errors); any call that still fails counts as an error execution, never as success.
- **Rationale**: matches FR-405/FR-407; precision/recall from labels makes the regex triage's blind spots visible next to the full agent.

## R6 — Prompt versioning
- **Decision**: `prompts/system/v001.md` holds the static block; `prompts/CHANGELOG.md` lists versions; `src/agent/system-prompt.ts` reads the newest `vNNN.md` at module load (sync, once), computes `PROMPT_VERSION = "v001+<sha256[:7]>"` and `buildSystemPrompt(ctx)` returns `{ text, version }` (static file + dated line). The orchestrator passes `promptVersion` through `Deps` for the turn; `hold-slot`, `confirm-booking` and `escalate-to-human` include it in their audit payloads when present; `LlmTurnInput.promptVersion` is recorded by the adapter (future trace attribute) and the report carries it.
- **Rationale**: an id + content hash makes "which instructions produced this" unambiguous even if someone edits a file without bumping the id (the hash changes; CI check that the id in the file name matches the CHANGELOG).
- **Alternatives**: hash only (opaque in reports), manual semver only (silently stale).

## R7 — README block and drift check
- **Decision**: markers `<!-- evals:start -->` / `<!-- evals:end -->` in README; `pnpm evals:readme` regenerates the block from `evals/reports/latest.json` (date, model, prompt version, commit, headline metrics, "authored golden set — no production data"); `pnpm evals:readme --check` exits non-zero when the block differs from a fresh render; the fake-mode CI job runs the check.
- **Rationale**: FR-408/FR-412; hand edits are impossible to miss.

## R8 — CI workflow and publication
- **Decision**: `.github/workflows/evals.yml`: job `fake` on every push/PR (postgres service, `pnpm evals:fake`, README check, uploads `evals/reports/*` as artifact); job `live` on `schedule` (weekly, Sunday 06:00 UTC), `workflow_dispatch` (inputs: model, repetitions, judge, cap), and `pull_request` with `paths: [prompts/**]` (amended 2026-10-08: PRs run live only when the `live-evals` label is applied, over `evals/live-subset.txt`; defaults 1 repetition / US$ 0.75) — skipped with a notice when `ANTHROPIC_API_KEY` is absent; on scheduled/dispatch success it creates or updates a branch `evals/report-<date>` with `evals/reports/latest.*` + regenerated README block and opens a PR via `gh` (no third-party action). Baseline is never written by automation.
- **Rationale**: spec Clarifications (cadence, repo keeps latest + baseline, PR publication); secrets never reach fork PRs by GitHub's rules.

## R9 — Judge
- **Decision**: `evals/lib/judge.ts` scores each live transcript's patient-facing replies for tone and clarity (1–5 each + one-line justification) with `prompts`-style versioned rubric `evals/judge/rubric.v1.md`, using `claude-opus-5-5` by default (different from the model under test), JSON answer parsed defensively; written into the report under `judge` with the rubric version; off unless `--judge`.
- **Rationale**: spec FR-410 and Clarification Q5.
